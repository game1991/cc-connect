1 daemon install 找不到 config.toml BUG FIXED ▶

现象

Warning: config.toml not found in $HOME
  Use --work-dir to specify the config directory or --config to point to the config file

明明 ~/.cc-connect/config.toml 存在，cc-connect config path 也能正确解析到它。

根因

daemon install 子命令的配置查找逻辑与主程序不同：

  • 主程序查找顺序：./config.toml → ~/.cc-connect/config.toml ✓
  • daemon install 只查找：$HOME/config.toml（直接在 HOME 下，不进子目录）✗

这是一个 bug —— daemon 子命令没有复用主程序的配置解析逻辑。

解决

# 临时方案 — 显式指定 --config
$ cc-connect daemon install --config "C:\\Users\\KC\\.cc-connect\\config.toml"
ℹ --work-dir 也可以，但需要指向 .cc-connect 目录，而非 HOME 目录。

已在 fork 中修复

分支 feat/role-based-tool-permissions，提交 a4558147：

  • cmd/cc-connect/daemon.go：增加与主程序一致的三级 fallback 配置解析（显式 --config → WorkDir/config.toml → ~/.cc-connect/config.toml）
  • daemon/manager.go：Config 新增 ConfigFile 字段
  • 三平台 launcher 均传递 --config：Windows PowerShell / systemd ExecStart / launchd ProgramArguments
✓ 修复后 daemon install 无需 --config 即可自动定位 ~/.cc-connect/config.toml。
2 配置文件迁移到其他盘后，用 Junction 链接回来行不行？ TIP ▶
✓ 结论：可行，Go 二进制和 Node.js 都能正常穿透 Junction 读取文件。

操作步骤

# 1. 移动实际数据
$ mv ~/.cc-connect/config.toml /other-drive/path/.cc-connect/config.toml

# 2. 删除空的源目录
$ rmdir ~/.cc-connect

# 3. 创建 Junction（无需管理员权限）
$ cmd //c mklink //J "C:\\Users\\KC\\.cc-connect" "D:\\msys64\\home\\KC\\.cc-connect"

注意事项

  • Windows Junction（mklink /J）不需要管理员权限，符号链接（mklink /D）需要
  • cc-connect config path 正确返回 $HOME\.cc-connect\config.toml
  • Junction 是文件系统级别的重解析点，所有程序透明访问，无兼容性问题

4 环境变量 ${WPS_XIEZUO_APP_SECRET} 报 "references unset variable" ENV ▶

现象

WARN config: env var placeholder references unset variable
  var=WPS_XIEZUO_APP_SECRET placeholder=${WPS_XIEZUO_APP_SECRET}

明明已在 ~/.bashrc 中 export 了该变量。

根因

MSYS2/bash 环境的特殊性：

  • 交互式登录 shell 才会 source .bashrc
  • Claude Code 的 Bash 工具每次在独立子 shell 中执行，不一定加载 .bashrc
  • Go 二进制（cc-connect.exe）继承的是调用进程的环境变量，不是 bash 的

解决

daemon install --config 后，cc-connect 会自动在 ~/.cc-connect 下生成一个 PowerShell launcher 脚本，该脚本正确加载环境变量。Task Scheduler 通过该 launcher 启动，环境变量可正常传递。

手动启动时需确保先 source：

$ source ~/.bashrc && cc-connect

6 MSYS2 bash 中执行 mklink 的正确姿势 TIP ▶

问题

MSYS2 bash 使用 Unix 风格路径，mklink 是 Windows 原生命令，路径需要 Windows 风格（反斜杠）。

正确写法

# 正确：用 //c 调用 cmd，路径用双反斜杠转义
$ cmd //c mklink //J "C:\\Users\\KC\\.cc-connect" "D:\\msys64\\home\\KC\\.cc-connect"

# 错误：单反斜杠会被 bash 转义吞掉
$ cmd //c mklink //J "$HOME\.cc-connect" "D:\msys64\home\KC\.cc-connect"

备忘

  • cmd //c — MSYS2 调用 Windows cmd 的标准写法（双斜杠转义）
  • mklink //J — Junction 类型（/J 在 MSYS2 中写成 //J）
  • 路径中的 \ — 在 bash 双引号中需要 \\ 转义
7 角色级工具权限控制（自建 fork） FORK ▶

背景

cc-connect 默认的 mode/allowed_tools 是 agent 级别配置，全角色共享。源码分析发现：

  • 权限审批（handlePendingPermission）不校验回复者身份，任何用户回复"允许"都能批准 ✗
  • admin_from 只控制特权斜杠命令（/shell 等），与工具权限审批无关 ✗

解决方案

三个核心改动：

  • 角色级 mode 和 allowed_tools — admin 用 yolo，readonly 用 dontAsk + 只读工具白名单
  • 权限审批身份校验 — 只有发起请求的用户或 admin 才能批准/拒绝
  • Bridge 卡片身份修复 — 通过参数传递真实 userID，默认身份为中性的 bridge-user
# 角色配置示例
[projects.users.roles.admin]
user_ids = ["your_admin_user_id"]
mode = "yolo"
disabled_commands = []

[projects.users.roles.readonly]
user_ids = ["*"]
mode = "dontAsk"
allowed_tools = ["Read", "Grep", "Glob", "LS", "LSP"]
disabled_commands = ["mode", "dir", "cd", "memory", "provider", "cron", "shell", "bind"]

Q9 daemon stop 停不掉进程怎么办？

现象

cc-connect daemon stop
# 无错误输出，但进程仍在运行
# 或: Stop failed: ...（schtasks 报错）

根因：上游 v1.3.3-beta.4 的 daemon stop 仅通过 schtasks /End 或 systemctl stop 发停止信号。进程非 schtasks 启动、或进程卡死时均会失败。

Fork 修复：增加 PID 回退杀进程逻辑

$ cc-connect daemon stop          # 优先级 1：schtasks 正常停止
$ cc-connect daemon restart --force  # 优先级 2：杀进程 → 等 500ms → 重启
$ ps -W | grep -i cc-connect     # 优先级 3：手动杀进程
$ taskkill /PID <PID> /F

回退流程：mgr.Stop() 失败 → LoadMeta() 读 ConfigFile → metaConfigPath() 解析 lock 路径 → KillExistingInstance() 验证进程映像名后终止。安全防护：KillExistingInstance 验证进程为 cc-connect.exe（Windows）或 cc-connect（Linux），防止 PID 重用误杀。

Q10 daemon restart --force 为什么更安全了？

旧版问题

问题场景后果
路径硬编码--config my-config.tomllock 文件名应为 .my-config.toml.lock，旧版用 .config.toml.lock
不等进程退出Kill 后立即 Restart旧进程占端口，新进程启动失败
PID 误杀风险PID 被新进程复用可能杀掉不相关进程

Fork 修复

  • metaConfigPath() — 从 daemon.json 读取 ConfigFile，支持任意配置文件名
  • 500ms sleep — Kill 后等待资源释放（端口、锁文件），再 Restart
  • 进程映像名验证 — Windows: QueryFullProcessImageNameW; Linux: /proc/<pid>/exe
Q11 daemon.json 中为什么路径是正斜杠？

Fork 版在 daemon install 保存 Meta 时对所有路径执行 filepath.ToSlash()，统一为正斜杠。理由：

  • 跨平台一致性 — daemon.json 可能被 WSL、SSH 远程、CI 等不同系统读取，正斜杠所有平台通用
  • JSON 可移植性 — 反斜杠在 JSON 字符串中需要转义（\\），正斜杠无需转义
  • TOML 配置兼容 — cc-connect 的 config.toml 也使用正斜杠，保持一致

Go 的 filepath.Join 和 os.Open 在 Windows 上同时接受 / 和 \，正斜杠路径不影响功能。
